# WF-017 - White-label rooms on a custom domain

- **Domain:** Room experience and content (`room-experience`)
- **Research source:** `docs/research/raw/room-experience.md` section 18
- **Distinct sources cited:** 3
- **Criticality:** supplementary
- **Why:** Branding. Commercially important to resellers, absent from the primary loop.
- **Branch:** `feature/WF-017-white-label-rooms-on-a-custom-domain`

## Research evidence

- **name:** White-label rooms on a custom domain
- **user_flow:**
  1. In your DNS host, add a **CNAME** record pointing to `custom-domains.qwilr.com` (Name: `proposals`; Type: CNAME; Value: `custom-domains.qwilr.com`).
  2. Wait for the CNAME to propagate ("It may take up to 24 hours").
  3. In the Qwilr dashboard: bottom-left sidebar → **Account Settings** → **Custom Domain**.
  4. Enter the domain — "It needs to be in a subdomain format", e.g. `proposals.acme.com` (not `acme.com`).
  5. Qwilr "will verify that the domain is available to use" → click **Save Custom Domain**.
  6. Optionally also set colours/fonts in **Brand Setup** and TypeKit or custom fonts.
  7. If using Cloudflare, set the CNAME to **DNS only** (turn off proxying) "in order to prevent the slow loading of your Qwilr pages."
- **data_flow:** Customer DNS CNAME → Qwilr custom-domain verifier → domain bound to the account → **all page links switch host** from `pages.qwilr.com` / `<account>.qwilr.com` to the customer's subdomain, with the page slug preserved and a mandatory security suffix appended: `proposals.acme.com/Proposal-Name-aB3xY9zK1q`. Existing links on the old host keep working. Re-pointing the custom domain later breaks previously shared links: "if you wish to change your custom domain again, all shared links would need to be reshared otherwise the links will appear broken."
- **data_sources:**
  - Customer **DNS host** (CNAME record)
  - `custom-domains.qwilr.com` (Qwilr's custom-domain target)
  - Qwilr **Account Settings → Custom Domain** (stored domain)
  - Qwilr **link secret** (per-page, non-removable URL suffix — "to the end of every page URL for security purposes")
  - Qwilr **brand settings** (colours, fonts, Adobe TypeKit)
- **apis_hit:** No public REST endpoint for custom domain or brand settings. The only documented URL-level guarantees are in the page API:
  - `GET /v1/pages/{pageId}` / `PUT /v1/pages/{pageId}` operate on `pageId` (pattern `^[a-z0-9]{24}$`), so host changes are transparent to API consumers.
  - A separate subdomain product exists for lower tiers: "Setting up a Custom Subdomain" (`help.qwilr.com/article/62-custom-subdomain`).
- **automations:**
  - **DNS-based activation:** the CNAME propagation delay is the only "job"; "You can still share the default **pages.qwilr.com** links during that time, and they'll continue to work."
  - **Automatic link-secret injection:** "Qwilr automatically appends a unique, non-removable identifier (*link secret*) to the end of every page URL for security purposes… This applies even after a custom domain is configured."
  - **Collaboration URLs bypass the custom domain:** "**Collaborator** page URLs won't use the custom domain, as they are for internal use only."
  - **Liferay's analogue** (different surface): a room's **Friendly URL** — "Determines the URL for this room. Changing it changes the room's address, so update any links that point to the old one."
- **features_tools:** DNS CNAME form; **Account Settings → Custom Domain**; domain-availability verification; **Save Custom Domain**; **Brand Setup** (colours & fonts); **Custom Subdomain**; Adobe TypeKit Fonts; Custom fonts; per-domain-provider DNS instruction links; Cloudflare proxying caveat; Qwilr's non-removable link secret.
- **extensibility:** Explicitly stated limit: "It does not produce fully custom slugs" — the vendor keeps a random suffix for share-link security, so white-labelling covers host + styling but not the final URL token. Documented cross-tenant hazard: changing the custom domain again invalidates all previously shared links, so a room product needs a domain-change migration path. Liferay adds the complementary primitives: **Friendly URL** for the readable slug plus **External Reference Code** as the stable integration key ("The *External Reference Code* is the key other systems use to find this room. Changing an existing value changes what those systems must send to reach the room. Confirm the new value with whoever maintains those systems before you save."), plus **Name**, and a read-only **Site ID**.
- **sources:**
  - https://help.qwilr.com/article/63-custom-domain
  - https://help.qwilr.com/category/544-setting-up-your-branding
  - https://learn.liferay.com/w/digital-sales-room/managing-rooms
- **evidence:**
  - "you can set up a Custom Domain so that your Qwilr Pages have a URL on your own domain — like **proposals.acme.com/xyz** (instead of qwilr.com/xyz or acme.qwilr.com/xyz)."
  - "A custom domain changes the domain portion of your Qwilr Page links… It does not produce fully custom slugs — Qwilr automatically appends a unique, non-removable identifier (*link secret*) to the end of every page URL for security purposes, e.g. proposals.acme.com/Proposal-Name-aB3xY9zK1q. This applies even after a custom domain is configured."
  - "add a new CNAME record and have it point to **custom-domains.qwilr.com**." / "It may take up to 24 hours for the CNAME redirect to fully work."
  - "Once you've added it, Qwilr will verify that the domain is available to use. Then click **Save Custom Domain.**"
  - "If you've previously shared any Qwilr Pages using our standard domain **pages.qwilr.com**, those links will continue working after your custom domain takes effect. However if you wish to change your custom domain again, all shared links would need to be reshared otherwise the links will appear broken."
  - "If you're using **Cloudflare**, make sure to turn off proxying for the CNAME entry and set it to **DNS only** in order to prevent the slow loading of your Qwilr pages."
  - Liferay: "**External Reference Code** — Enter a unique key for referencing the room from other systems." / "**Friendly URL** — Determines the URL for this room. Changing it changes the room's address, so update any links that point to the old one." / "**Site ID** — Shows Liferay's read-only identifier for the room's site."

### Implementation notes

Two questions the research left open were put to Jev rather than guessed at.
Both are recorded in `orchestration/decisions/jev-audit.jsonl`.

- **`secret_is_identity` (p=0.99).** The research names the hazard — "if you
  wish to change your custom domain again, all shared links would need to be
  reshared otherwise the links will appear broken" — but not the resolution. The
  link secret is the room's identity and the host is presentation, so
  re-pointing a domain rewrites the address and breaks nothing. A first,
  narrower framing of the question returned `verdict=uncertain`; that was not
  overridden. More evidence was gathered (Liferay's split between Friendly URL
  and External Reference Code, and Qwilr's own non-removable secret) and the
  question re-asked.
- **`room_scoped_with_account_facade` (p=0.98).** The vendor binds a domain per
  account, but this product's envelope is room-centric. The domain is room
  scoped; grouping rooms by a shared value is left to the existing dynamic
  index, so no account concept and no migration is introduced.

Sourced behaviour and design inference are kept separate in the module
docstrings. Two things are **inference, not sourced**:

- The canonical CNAME target. The vendor points customers at
  `custom-domains.qwilr.com`, which is their edge. This product needs its own,
  so it is a deployment setting (`DSR_CNAME_TARGET`) defaulting to an RFC 2606
  `.invalid` placeholder that can never resolve.
- *How* a domain is verified. The research says only that the vendor "will
  verify that the domain is available to use". This implementation checks that
  the host resolves to the canonical target and that no other live room has
  claimed the domain. That shows the record exists; it does not prove control of
  the domain. A production deployment should add a DNS TXT challenge, which is
  called out in `backend/dsr/domain_service.py` rather than claimed as secure.

Outstanding: the browser pass. The `bsk` daemon is running but no browser is
connected to it and no desktop browser is attached to the agent session, so the
visual and responsive checks in the design-system pre-delivery list have not
been done. That needs a human.

## Port to the plugin host

Ported onto the feature host from
`feature/WF-017-white-label-rooms-on-a-custom-domain`. The research above is
unchanged; this section records what the port changed and what it could not.

- **Backend:** `backend/dsr/features/wf_017_white_label.py`,
  `id = wf-017-white-label`, `router.prefix = /api/wf-017-white-label`. All ten
  routes moved from `@app.<verb>` on the shared app to `@router.<verb>`. The two
  `@app.exception_handler` blocks became an `EXCEPTION_HANDLERS` export, and the
  `app.state.domain_service` instance became a dependency declared in the
  feature, because both needed `dsr/api.py` and that file is shared.
- **Frontend:** `frontend/src/features/wf-017-white-label/`, discovered by the
  glob in `lib/features.js`. `App.jsx` and `lib/api.js` are untouched; the ten
  API calls the branch added to the shared `api` object are now in the feature's
  own `api.js`, on `apiRequest`.
- **Prefix change.** The branch served `/api/white-label/*` and
  `/api/rooms/{room_id}/white-label*`. Both are core vocabulary other workflows
  want, so the port owns `/api/wf-017-white-label/*` and
  `/api/wf-017-white-label/rooms/{room_id}/white-label*`. The branch was never
  merged, so no external caller depended on the old paths.
- **A defect the port fixed.** The branch built each write's audit `source`
  inside `DomainService` (`source=f"claim custom domain {domain} for {room}"`),
  so the audit log named paths the app did not serve — the same bug the port
  brief names, which has already shipped once in this project. `source` is now a
  required keyword-only argument on every writing method, supplied by the route
  from `router.prefix`, and
  `test_an_audit_source_names_a_route_the_app_actually_serves` asserts the
  invariant rather than a list of strings.
- **One deviation from the port brief, on purpose.** The brief names the module
  `backend/dsr/features/wf_017-white-label.py`. It is
  `wf_017_white_label.py` here, because `docs/FEATURE-CONTRACT.md` specifies
  `<ticket>_<slug>.py` and all thirteen sibling modules use underscores. The
  host would load a hyphenated name perfectly well — it imports by string — which
  is exactly what makes it a trap: the file serves every route and cannot be
  reached by any ordinary import statement, because a hyphen is not an
  identifier character. `test_the_feature_module_is_named_the_way_the_contract_names_it`
  pins the convention.

### What a reader must not conclude from "the tests pass"

The tests pass on `127.0.0.1`, and that is a much weaker claim than
"white-label domains work". Not true in the test environment, and required in
production:

- **A reverse proxy terminating TLS, with a certificate per customer domain.**
  Share URLs are built as `https://<claimed domain>/r/...`, so a browser will
  refuse them without a certificate. Nothing in this repository issues one.
- **A wildcard or per-customer DNS record.** The customer points a CNAME at the
  deployment's canonical target (`DSR_CNAME_TARGET`), and that host has to
  resolve to the same edge that serves the app, for every customer at once.
- **Host-header routing that forwards rather than redirects.** `GET
  /api/wf-017-white-label/links/{secret}` reads the `Host` header and answers
  404 `host_not_served` for a host this deployment does not claim. A proxy that
  normalised or dropped the header would break exactly the guarantee the
  `secret_is_identity` decision exists to provide.
- **A path-routing seam in the frontend.** The buyer-facing path
  `/r/<slug>` is a real URL path, and `App.jsx` resolves only `location.hash`.
  The port works around this inside its own feature folder
  (`mountShareLinkIfRequested` in `index.jsx`) and reports it as a finding: the
  host needs a `matchPath` hook, and until it has one, a buyer link depends on
  that workaround rather than on the product.
- **A DNS TXT challenge.** Unchanged from the original implementation note above
  and still not implemented: verification proves a CNAME exists, not that the
  account controls the domain.

# Port brief: WF-001 - Create room from template

**The hold on this workflow is lifted. Start it.**

## Why it was held, and what resolved it

This workflow sat unbuilt because its branch edits `backend/dsr/db/audited.py` —
the wrapper where the guarantee that the audit row is written in the same
transaction as the change actually lives. A port is a mechanical transformation,
and that is the wrong instrument for deciding what a change to the audit core
means.

It has now been read and measured, and the hold was wrong.

**What the branch actually adds to the core is a missing host capability, not a
domain concept.** It adds `AuditedDatabase.transaction()` — N audited writes in
ONE all-or-nothing transaction, each still getting its own audit row — plus
`AuditedWriter` and a `_tx_depth` guard that **refuses** single-record writes
while a transaction block is open, so the guarantee cannot be quietly bypassed.

Its own docstring says why the host needs it: *"A workflow that must produce more
than one record — a room and the site it is bound to, say — cannot half-succeed
through this handle."* That is this workflow's exact requirement, and it is the
core's own guarantee generalised from one change to several.

So it was promoted into the host deliberately, as a labelled `platform-change`,
with its tests. **That is already merged: PR #41, commit `182f56e`.**

Verified on `main`, read back out of `git show`:

    def transaction      ON MAIN
    class AuditedWriter  ON MAIN
    _tx_depth guard      ON MAIN   (refuses a single write inside a transaction)
    def count_where      ON MAIN
    def bulk_delete      ON MAIN

Jev agreed: `promote_deliberately` at confidence **0.99**, margin 1.00 over the
runner-up.

## The file name you own

Your branch adds `backend/dsr/rooms.py`. **WF-005 also adds it.** It has been
decided, by measurement and confirmed by Jev at confidence 1.00:

> **WF-005 keeps `backend/dsr/rooms.py`.** It is the larger module and defines
> the room *state machine* — `RoomWorkflow`, `status_of`, `available_actions`,
> `capabilities_for`, `Principal` — which is a room's own vocabulary. Your
> `create_room` needs somewhere to put a room's status, and if that vocabulary
> lives in a differently-named module then every room creation reaches across a
> boundary for it.

**Your module is `backend/dsr/room_templates.py`.** That is what it is: a
template-to-room wizard with `list_templates`, `find_template`, `slugify`,
`_validate_friendly_url`, `_friendly_url_is_taken`, `create_room`. It must not
try to import a room's status vocabulary from a module that does not exist yet —
WF-005 is landing separately. If you need to represent a room's state, put it in
your own records; the storage layer is schema-flexible by design and a team
adding a field must not need coordination with anyone.

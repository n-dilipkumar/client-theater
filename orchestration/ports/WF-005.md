# Port brief: WF-005 - Archive and restore a room

**The hold on this workflow is lifted. Start it.**

## Why it was held, and what resolved it

This workflow sat unbuilt because its branch edits `backend/dsr/db/audited.py` —
the wrapper where the guarantee that the audit row is written in the same
transaction as the change actually lives. A port is a mechanical transformation,
and that is the wrong instrument for deciding what a change to the audit core
means.

It has now been read and measured, and the hold was wrong.

**What the branch adds to the core is a missing host capability, not a domain
concept.** It adds `bulk_delete()` — many records in ONE transaction with ONE
audit row — and a matching `Store.bulk_delete` facade.

Its own docstring says why the host needs it: *"Deleting a room and the documents
it owns one call at a time would let the audit log describe work that only partly
happened, which is the exact failure mode the single-transaction guarantee exists
to prevent."* Archiving a room is a cascade. Without this primitive the audit log
can describe work that only partly happened, which is the precise thing the
product does not do.

So it was promoted into the host deliberately, as a labelled `platform-change`,
with its tests. **That is already merged: PR #41, commit `182f56e`.**

Verified on `main`, read back out of `git show`:

    def bulk_delete     ON MAIN
    def count_where     ON MAIN
    def transaction     ON MAIN   (from WF-001, same platform change)

Jev agreed: `promote_deliberately` at confidence **0.99**, margin 1.00 over the
runner-up.

## Tests are not optional

The research document is `docs/research/digital-sales-room-workflows/wf/WF-005.md`.
Read it in full before writing anything. It carries the user flow, data flow,
data sources, APIs hit, automations, features and tools, extensibility, and
quoted evidence for each. Those decisions are already made and sourced; your job
is to land them, not to revisit them.

The branch carried `backend/tests/test_rooms.py` — bring those tests across as
the base, and add coverage for what the core change makes possible and previously
impossible:

* a room and the documents it owns are archived in ONE transaction with ONE audit
  row, and the dynamic index reflects it;
* a cascade that hits a missing id rolls the whole thing back, leaving no partial
  state and no audit row describing work that did not fully happen;
* `bulk_delete` defaults to soft delete and keeps the index queryable;
* archiving is a state change `Active -> Archived`, and restore is its inverse —
  including what happens when a room is restored whose site has since been
  removed;
* `available_actions` and `capabilities_for` refuse what the principal is not
  entitled to, with `RoomForbidden` rather than a silent no-op.

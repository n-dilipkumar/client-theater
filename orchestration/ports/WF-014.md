# Port brief: WF-014 - Expire or cap access to a room

**The hold on this workflow is lifted. Start it.**

## Why it was held, and what resolved it

This workflow sat unbuilt because its branch edits `backend/dsr/db/audited.py` and
`store.py` — the wrapper where the guarantee that the audit row is written in the
same transaction as the change actually lives, and the facade over it. A port is
a mechanical transformation, and that is the wrong instrument for deciding what a
change to the audit core means.

It has now been read and measured, and the hold was wrong.

**What the branch adds to the core is a missing host capability, not a domain
concept.** It adds `count_where()` — the counting twin of `find()`, resolving
dotted JSON paths through the dynamic index — plus a matching `Store.count_where`
facade.

Its own docstring says why the host needs it: *"So a caller that needs an
aggregate over schema-flexible data does not have to fetch rows to measure them,
and does not have to reach around this wrapper to write the SQL itself."* A cap on
access is exactly an aggregate over schema-flexible data.

This gap was already known and already recorded. **WF-009, which is merged, said
so in its own commit message:** *"The other, count, has no honest equivalent on
the facade ... a capped `len(list(...))` would quietly downgrade it."* A shipped
feature had documented a missing primitive and worked around it. That workaround
is now unnecessary.

So it was promoted into the host deliberately, as a labelled `platform-change`,
with its tests. **That is already merged: PR #41, commit `182f56e`.**

Verified on `main`, read back out of `git show`:

    def count_where     ON MAIN   (in both audited.py and store.py)
    def bulk_delete     ON MAIN
    def transaction     ON MAIN   (from WF-001, same platform change)

Jev agreed: `promote_deliberately` at confidence **0.99**, margin 1.00 over the
runner-up.

## Tests are not optional

The research document is `docs/research/digital-sales-room-workflows/wf/WF-014.md`.
Read it in full before writing anything. It carries the user flow, data flow,
data sources, APIs hit, automations, features and tools, extensibility, and
quoted evidence for each. Those decisions are already made and sourced; your job
is to land them, not to revisit them.

Bring across `test_access.py` and `test_access_api.py` from the branch, and cover
what the core change makes possible:

* a cap is counted with `count_where` over the dynamic index, not by fetching rows
  and truncating — the gap WF-009 had recorded;
* `count_where` agrees with `find` for the same conditions, including numbers and
  booleans, and excludes soft-deleted rows by default;
* expiry at a UTC boundary, and the difference between "expires at" and "capped
  at" when a room has both;
* what a buyer sees once access has lapsed, which is the part of this workflow a
  user actually experiences.
